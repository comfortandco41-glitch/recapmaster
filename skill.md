# Promovie Recap Tool — skill.md

## Purpose

Promovie Recap is a media-processing application that turns a user-provided YouTube or Bilibili video into a recap-style video with:

1. Source video download
2. Audio extraction
3. Whisper transcription
4. SRT subtitle generation
5. Voice generation using VoxCPM 2 through a Google Colab inference endpoint
6. FFmpeg-based video/audio composition
7. Optional recap-oriented visual editing
8. Final video download
9. Automatic cleanup of temporary files and expired jobs

> **Rights and copyright requirement:** The application must only process content the user has permission or a lawful basis to download, transform, and redistribute. Visual transformations such as zooming, freezing, flipping, cropping, or speed changes must not be presented as a method to bypass copyright enforcement or guarantee that a video will be "copyright free." The product should describe them as recap/editing features.

---

## Core User Flow

```text
User enters YouTube/Bilibili URL
        ↓
Validate URL + create Job
        ↓
Download source media
        ↓
Extract/normalize audio
        ↓
Whisper transcription
        ↓
Generate SRT
        ↓
Send transcript/script to VoxCPM 2
        ↓
Generate narration audio
        ↓
Normalize narration + align timing
        ↓
FFmpeg video transformation
        ↓
Mix/replace audio
        ↓
Render final MP4
        ↓
Quality check
        ↓
User downloads result
        ↓
Delete temporary source/cache/render files
```

---

## Supported Input

### YouTube

Accept normal YouTube video URLs.

Examples:

- `https://www.youtube.com/watch?v=VIDEO_ID`
- `https://youtu.be/VIDEO_ID`

### Bilibili

Accept supported Bilibili video URLs.

The downloader layer must be modular because source platforms can change their extraction behavior.

### URL validation

Reject:

- Unsupported domains
- Empty URLs
- Malformed URLs
- URLs that cannot be accessed by the configured downloader
- Downloads that exceed configured duration/file-size limits

Do not accept arbitrary URLs as shell commands.

# Pipeline Skills

## 1. Job Creation

Every processing request receives a unique `job_id`.

Example:

```text
job_20260919_8f31a
```

Persist only the metadata required to track the job.

Recommended job states:

```text
QUEUED
DOWNLOADING
DOWNLOADED
TRANSCRIBING
TRANSCRIBED
VOICE_GENERATING
VOICE_READY
RENDERING
RENDERED
READY
FAILED
CLEANING
DELETED
```

The frontend polls or subscribes to job progress rather than keeping one HTTP request open for the entire render.

---

## 2. Source Downloader

Recommended implementation:

- `yt-dlp` for supported YouTube/Bilibili extraction
- FFmpeg for container/audio conversion

Downloader responsibilities:

```text
URL
 ↓
Validate source
 ↓
Resolve media
 ↓
Download into job-specific temporary directory
 ↓
Return local source path + metadata
```

Store:

```json
{
  "job_id": "job_x",
  "source_platform": "youtube",
  "source_url": "...",
  "duration_seconds": 3600,
  "source_path": "/jobs/job_x/source.mp4"
}
```

Never expose internal filesystem paths to the browser.

---

## 3. Audio Extraction

Use FFmpeg to extract speech-friendly audio.

Recommended target:

```text
Mono
16 kHz
PCM WAV
```

Example conceptual command:

```bash
ffmpeg -i source.mp4 \
  -vn \
  -ac 1 \
  -ar 16000 \
  -c:a pcm_s16le \
  audio.wav
```

The exact command should be generated by the backend rather than accepted from the user.

---

# 4. Whisper Transcription

Use Whisper to transcribe the extracted audio.

Input:

```text
audio.wav
```

Output:

```json
{
  "language": "en",
  "segments": [
    {
      "start": 0.0,
      "end": 4.8,
      "text": "..."
    }
  ]
}
```

The transcription service should preserve timestamps.

---

## 5. SRT Generation

Convert Whisper segments into valid SRT.

Example:

```srt
1
00:00:00,000 --> 00:00:04,800
First sentence.

2
00:00:04,800 --> 00:00:09,200
Second sentence.
```

SRT requirements:

- Sequential numbering
- Valid timestamps
- UTF-8
- No overlapping segments unless explicitly supported
- Escape/normalize problematic control characters

Keep the original Whisper JSON internally because it is useful for timing alignment.

---

# 6. Recap Script Layer

The product can optionally create a recap script from the transcript.

Recommended pipeline:

```text
Whisper transcript
       ↓
Transcript cleanup
       ↓
Recap summarization
       ↓
Narration script
       ↓
Voice generation
```

Do not silently replace the transcript with an AI-generated script.

Store both:

```text
original_transcript
recap_script
```

This makes debugging and user review possible.

---

# 7. VoxCPM 2 Voice Generation

VoxCPM 2 runs externally through a user-configured Google Colab inference service.

The application should treat VoxCPM as an external provider.

Recommended abstraction:

```typescript
interface VoiceProvider {
  generateSpeech(input: {
    text: string;
    voice?: string;
    language?: string;
  }): Promise<{
    audioPath: string;
    durationSeconds: number;
    sampleRate: number;
  }>;
}
```

The application must not hard-code a temporary Colab URL.

Use an environment variable:

```env
VOXCPM_ENDPOINT=https://<configured-endpoint>
VOXCPM_API_KEY=<optional-secret>
```

Recommended request:

```json
{
  "text": "Narration text...",
  "language": "en",
  "voice": "default"
}
```

Recommended response:

```json
{
  "audio_url": "https://...",
  "duration_seconds": 18.4,
  "sample_rate": 24000
}
```

The backend downloads the generated audio into the job workspace.

### Important

Google Colab sessions can disconnect, sleep, restart, or change their public endpoint. Production architecture should therefore support replacing the Colab provider later with:

- a dedicated GPU service
- Cloud Run GPU where appropriate
- another inference server
- a self-hosted VoxCPM service

# 8. Narration Timing

Generated narration will rarely have exactly the same duration as the original speech.

The renderer should support:

```text
Original video duration
Narration duration
```

Strategies:

### Strategy A — narration-driven recap

The video is cut into recap sections and the narration becomes the primary timing source.

### Strategy B — original-duration narration

Adjust narration timing with FFmpeg `atempo` within safe limits.

### Strategy C — section-level alignment

Generate one narration clip per recap paragraph/section and map each section to selected video segments.

For a movie recap product, section-level alignment is recommended.

# 9. Video Transformation

FFmpeg is responsible for the final composition.

Possible recap-editing effects:

- crop
- scale
- subtle zoom in
- subtle zoom out
- horizontal flip
- short freeze-frame
- scene trimming
- aspect-ratio conversion
- mild speed adjustment
- letterbox/pillarbox handling
- transitions
- audio replacement or mixing

These effects should be configurable per segment.

Example:

```json
{
  "segment": 4,
  "effects": [
    {
      "type": "zoom",
      "direction": "in",
      "duration": 2.5,
      "amount": 1.08
    },
    {
      "type": "flip",
      "axis": "horizontal"
    }
  ]
}
```

Avoid extreme or constant effects. The editing system should prioritize watchability and narrative clarity.

# 10. Copyright / Rights-Safe Product Behavior

The application must not claim:

- "This makes copyrighted content legal."
- "This guarantees no Content ID claim."
- "This bypasses copyright detection."
- "This makes any movie safe to upload."
- "Flipping/zooming/freeze frames removes copyright."

Instead display a rights notice such as:

> Only upload or process videos you have permission or a lawful basis to use. Editing, transforming, narrating, or changing audio does not automatically remove copyright restrictions.

If the application has publishing functionality, require a confirmation checkbox before processing:

```text
[ ] I confirm that I have the necessary rights or permission
    to process and use this source video.
```

# 11. Rendering

Recommended rendering stages:

```text
source.mp4
   ↓
selected video segments
   ↓
visual effects
   ↓
narration audio
   ↓
optional background/music audio
   ↓
final.mp4
```

Recommended output:

```text
MP4
H.264 video
AAC audio
```

The renderer should write to:

```text
/jobs/<job_id>/render/final.mp4
```

Never render directly into a shared public directory.

# 13. Error Handling

Every pipeline stage must produce structured errors.

Example:

```json
{
  "code": "VOICE_PROVIDER_UNAVAILABLE",
  "stage": "VOICE_GENERATING",
  "message": "Voice generation service is temporarily unavailable.",
  "retryable": true
}
```

Retry:

- network download errors
- temporary provider errors
- transient FFmpeg failures

Do not blindly retry:

- invalid URLs
- unsupported formats
- permission errors
- corrupted media
- invalid user configuration

---

# 14. Cache and Cleanup

Each job gets an isolated workspace:

```text
/jobs/
  job_abc/
    source/
    audio/
    transcript/
    voice/
    render/
    logs/
```

After successful download by the user:

```text
delete:
  source/
  audio/
  transcript/
  voice/
  render/
```

Also run a cleanup worker for abandoned jobs.

Example policy:

```text
QUEUED/PROCESSING jobs:
  retain while active

READY jobs:
  retain for 30-60 minutes after completion

FAILED jobs:
  retain logs temporarily

Expired jobs:
  delete all media and temporary files
```

Never rely only on the frontend's "download completed" event. Use TTL cleanup as a safety net.

# Security Requirements

## Command Injection

Never concatenate user input into shell commands.

Bad:

```text
ffmpeg -i "<user_url>"
```

Good:

- Validate URL
- Resolve download through a controlled downloader
- Pass arguments as an argument array
- Use fixed output directories

## File Isolation

Every job must have its own UUID directory.

## File Size Limits

Configure:

```text
MAX_SOURCE_SIZE_MB
MAX_DURATION_SECONDS
MAX_OUTPUT_SIZE_MB
MAX_CONCURRENT_JOBS
```

## SSRF Protection

Do not allow the downloader or internal HTTP client to access arbitrary private network addresses.

Only allow supported media domains and configured service endpoints.

## Authentication

If the product has accounts, every job must belong to a user:

```text
user_id → job_id → files
```

Users must never be able to access another user's job.

# Definition of Done

A job is complete only when:

- Source downloaded successfully
- Audio extracted
- Whisper transcription generated
- SRT generated
- Narration generated
- Video rendered
- Audio/video duration is valid
- Final MP4 can be opened
- Final file exists
- Download endpoint works
- Cleanup is scheduled
- Job status is `READY`
